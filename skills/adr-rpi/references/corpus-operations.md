## The model

The corpus is an **append-only log with a compacted projection**, in the Kafka
sense. Not context compaction, and emphatically not `VACUUM`:

| | Kafka log compaction | This corpus |
|---|---|---|
| Log | Partition segments, append-only | ADR files, one per decision |
| Key | Message key | The decision's topic — its components |
| Retained value | Latest value per key | Latest `Accepted` ADR per topic |
| Projection | Compacted topic | `INDEX.md`, `CONSTRAINTS.md` |
| Source data | Never mutated in place | Never mutated in place |

The consequences worth internalizing: source files are never rewritten, every
derived artifact is regenerable from source and therefore safely deletable, and
the projection is a *read* optimization with no authority of its own. If a
projection and an ADR disagree, the ADR is right and the projection is stale.

## The two derived artifacts

| Artifact | Produced by | Rule |
|---|---|---|
| `INDEX.md` | `scripts/adr_index.py`, from frontmatter | Deterministic. No model involvement, so no drift. Byte-identical on regeneration. |
| `CONSTRAINTS.md` | The model | Regenerated **wholesale** from source, never edited in place. Header must say it is generated. |

The split is the point. Anything a script can compute — status, components,
dates, supersession links, titles — belongs in `INDEX.md`, where it cannot be
subtly wrong. `CONSTRAINTS.md` needs judgment (turning a decision into a
prohibition), so a model writes it, and it is therefore treated as disposable
output rather than a record.

Regenerate both with:

```bash
python3 <skill>/scripts/adr_index.py docs/adrs        # deterministic
python3 <skill>/scripts/adr_chain.py docs/adrs --validate
```

`--check` instead of a plain run tells you whether `INDEX.md` is stale without
writing it, which is what CI wants.

## CONSTRAINTS.md

Build this one first when the corpus warrants a projection at all, because it
answers what the research phase actually needs. Not "what did we decide" —
`INDEX.md` covers that — but **"what am I not allowed to do here."**

**When it is worth having:** roughly eight or more active ADRs covering the
components in play. Below that, research reads the ADRs directly; a digest of six
files is a lossy copy of something cheap to read in full. If your corpus never
crosses that line, this file never needs to exist, and that is a healthy outcome
rather than a missing feature.

**How to generate it:** read every active ADR, then write the file from scratch.
Never edit it incrementally — an incrementally-edited projection accumulates
drift from the source it claims to summarize, which is the exact failure the
generated/derived split exists to prevent.

Required shape:

```markdown
<!-- GENERATED by the adr-rpi skill from the ADRs in this directory.
     Regenerated wholesale, never edited in place. Do not edit: your changes are
     lost on the next regeneration. The ADRs are the source of truth. -->

# Active constraints

## checkout, sessions

- Checkout session state lives in Redis, not Postgres — no new session columns.
  (2026-07-24-redis-session-store)
- Sessions expire after 30 minutes; no code may extend a session past that.
  (2026-07-24-redis-session-store)

## billing

- Money is integer minor units end to end. No floats in billing paths.
  (2026-03-02-integer-minor-units)
```

Every constraint carries its ADR id. That is what lets an agent drill into the
reasoning when it needs to argue with a constraint rather than just obey it — a
prohibition with no traceable why gets rationalized around.

Write constraints as prohibitions and invariants, in the imperative. "Sessions
live in Redis" is a fact; "no new session columns in Postgres" is a constraint.
The second one changes behavior.

## The tiered read

```bash
python3 <skill>/scripts/adr_chain.py docs/adrs --relevant checkout,sessions
```

Relevance comes from the `components` frontmatter, deterministically — not from a
model's guess about which filenames look related.

| Tier | What to do |
|---|---|
| `Accepted`, relevant components | Read in full |
| `Accepted`, other components | One-line row in `INDEX.md` |
| `Proposed` | Read and flag — a decision is in flight and may collide |
| `Superseded` | Do not read; the live ADR carries the conclusion forward |

For any old id, `adr_chain.py docs/adrs --head <id>` returns the live ADR at the
end of its chain, so stumbling on stale history costs one hop rather than a read
of the whole chain.

Cite the ids you consulted in the research report. Consultation you can't audit
is consultation you can't trust.

## Superseding a decision

Supersession is the only way an accepted decision changes, and it sits behind the
same human gate as acceptance — same weight of decision, opposite direction.

1. **Author the successor** with `status: Proposed`, `supersedes: [<old-id>]`, and
   a Context section stating what changed since the original. Do not touch the old
   ADR yet.
2. **Stop at the gate.** Name the ADR being invalidated and what it costs.
3. **On human approval only:** set the successor to `Accepted`; set the old ADR's
   `status: Superseded` and `superseded-by: <new-id>`. Those three fields are the
   entire permitted mutation surface of an accepted ADR.
4. **Regenerate and validate.** `adr_chain.py --validate` rejects one-sided links,
   dangling references, status/pointer mismatches, and cycles. A supersession
   recorded on only one end is how a decision quietly disappears, and it is the
   specific thing this validator exists to catch.

Chains collapse deterministically from frontmatter: given A → B → C, an agent
reads C and can see that A and B exist as history without reading them.

## Archiving

Moving a `Superseded` ADR into `docs/adrs/superseded/` is always safe: it changes
the path, not the content, and it keeps globs over the active directory honest.
The scripts read both locations and generate links accordingly. Archiving is
optional — a superseded ADR left in place validates fine. Archiving something that
is *not* superseded is an error, and the validator says so.

## Regenerate on write

Regenerate when an ADR is added or a status flips — not when the corpus reaches
some size. A projection that refreshes on a size threshold is stale exactly when
you have started relying on it.

The skill body does this inline at Gate 2 and Phase 5, which is enough for
interactive use. To make it hold for edits made outside the workflow, wire one of
these into the *target* repo (not into this skill, which cannot reach across
repos):

A `PostToolUse` hook in the target repo's `.claude/settings.json`:

```json
{
  "hooks": {
    "PostToolUse": [
      {
        "matcher": "Write|Edit",
        "hooks": [
          {
            "type": "command",
            "command": "case \"$CLAUDE_TOOL_INPUT_FILE_PATH\" in *docs/adrs/*.md) python3 path/to/adr_index.py docs/adrs;; esac"
          }
        ]
      }
    ]
  }
}
```

Or a CI step, which catches human edits too:

```bash
python3 path/to/adr_index.py docs/adrs --check   # fails if INDEX.md is stale
python3 path/to/adr_chain.py docs/adrs --validate
```

Neither is installed for you. Offer it; don't assume it.

## Why the corpus is never rewritten

Git keeps history, but the working tree is what the next agent reads. A constraint
removed from the tree is functionally gone even though it is technically
recoverable — nobody runs `git log` on a decision they don't know existed.

That gap is why "never delete or rewrite ADR source" is an invariant rather than
a preference. The dangerous case is not malice, it is an agent that finds a
decision inconvenient and sincerely consolidates it away while tidying up. The
rule holds hardest exactly when removing the ADR would make the current task
easier.

Two habits follow. Keep the significance bar high, so the corpus stays small
enough that nobody feels the urge to prune it — a corpus that needs aggressive
collapsing usually has a significance-bar problem, not a compaction problem. And
scope ADRs by component, so relevance filtering does the work that deletion would
otherwise be reached for.
